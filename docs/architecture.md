# 架构与数据来源

## 运行结构

`CodexUsageMonitor.exe → runtime/node.exe collector.cjs`。

npm 命令从包内启动同一 EXE，并将 `CODEX_MONITOR_DATA` 指向用户数据目录。ZIP 默认保持便携式布局。

C# 主程序用命名互斥量保证单实例，并通过限当前用户的命名管道接收后续启动指令。EXE 承载主窗、小窗、托盘和动效；Node.js 子进程通过标准输入输出交换 JSON 行。系统进程采样使用同一 EXE 的后台 WMI 子命令，只传递用于关联的会话标识。

| 模块 | 职责 |
| --- | --- |
| `collector.cjs` | 增量读入日志、只读查询 Codex 数据库、保存本程序缓存和采样进程 |
| `realtime.cjs` | 文件监听、每秒签名检查、120 ms 合并窗口、串行采集队列 |
| `activity.cjs` | 按会话与回合保存活动、终态保留和本地确认 |
| `questions.cjs` | 提取问题 ID，匹配真实回复 |
| `speed.cjs` | 窗口速率、最新回合、命令区间并集和活动判定 |
| `calibration.cjs` | 校准样本、拟合、时序验证和占比估算 |
| `monitor.ps1` / `ui-state.ps1` | 原生界面、增量表格通知、搜索、详情及托盘 |
| `mini.ps1` / `mini-motion.ps1` | 小窗、原生毛玻璃、会话排序与动画生命周期 |
| `demo.ps1` | 与正式小窗共用组件的模拟状态演示 |

## 两类更新

快速更新只处理变化的日志及状态，发送 `activity` 消息。完整统计按用户配置发送 `snapshot`。配额数值或周期变化时，快速更新也会发送完整统计。Windows 进程采样完成后独立发送 `processes`。界面更新复用现有行和图形对象。

同一时刻只执行一个 SQLite 采集任务。扫描期间到达的变化会合并后继续处理。监听失效时由文件签名检查补漏；手动模式同时暂停监听和定时采集。

## 来源与优先级

| 内容 | 来源 |
| --- | --- |
| 会话元数据与关联 | 版本化的 `state_*.sqlite` 与会话日志 |
| token 与配额快照 | `token_usage_record`、旧格式累计计数及配额事件 |
| 轮次开始、完成、中断 | 日志事件与 `thread_history_1.sqlite.thread_turns` |
| 待回答问题 | 已接受的异步问题调用、历史问题记录、用户回复中的问题 ID |
| 客户端已读 | `thread_read_receipts`，只读 |
| Windows 进程 | CIM 的进程与父进程信息 |

迟到的历史投影不能覆盖更新的日志终态或清除尚未同步到历史库的问题。命令失败与整个回合失败分别处理。用户点击终态行产生本程序的本地确认；它与客户端已读回执分开记录。

## 集成边界

2026-11-16 核对本机客户端版本 `26.1111.2228.0`，已验证 `codex://threads/<UUID>` 系统协议。当前运行实例未提供可供外部监控器附加的公开只读事件端点，因此状态更新依赖本地持久化记录。

权限审批、部分 MCP 交互等仅存在于客户端运行时的状态，当前版不作推断。未来接入事件流时仍需确认连接的是用户正在使用的同一个实例。

## 维护约定

界面与采集器读取 `src/version.json`，npm 元数据读取 `package.json`；测试和打包会检查两者版本一致。快照的 `version: 1` 是消息结构版本，独立维护。程序自己的 SQLite 架构版本由迁移逻辑管理。

发布文件使用清单列举，包内 `manifest.json` 记录每个文件的 SHA-256。修改源码后先运行测试，再重新打包；不要直接修改 `outputs/` 中的程序作为下一版源码。
